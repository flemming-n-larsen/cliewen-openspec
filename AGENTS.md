# Repository conventions

Write all repository content in US English, including documentation, examples, prompts, comments, and user-facing messages. Conversation with a user may use the user's preferred language.

Apply these writing rules to all text you create or edit, including plain-text files, Markdown, change proposals, specs, tasks, code comments, docstrings, commit messages, pull-request descriptions, user-facing messages, and conversational replies. Adapt the explanation to the intended reader and format without assuming knowledge of the conversation. Lead change descriptions with the problem, resulting behavior, and practical impact. Use plain language and concrete examples; explain unfamiliar terms. Include technical details when they explain behavior, constraints, risks, or tradeoffs. Link references using their ID and descriptive title, explaining relevance where needed. State each fact once and link to supporting detail. Remove filler and repetition while preserving requirements, acceptance criteria, important exceptions, and required artifact sections. Preserve machine-readable syntax and exact identifiers. PR descriptions include relevant validation and limitations. Review clarity and brevity before finishing; there is no fixed word limit.

Across these texts, prefer embedded Mermaid when a diagram makes relationships or behavior easier to understand. Use ASCII or plain-text blocks where clearer, especially for directory trees and small sketches, or where Mermaid cannot render. Keep a short explanation beside diagrams and maintain one authoritative representation. A diagram is optional when prose or a table is clearer.

Adapt these rules to the format. Code comments explain intent, constraints, or surprising behavior instead of restating the code. Commit messages summarize the concrete change; add rationale or consequences in the body when useful. Use diagrams only where the format supports them and they improve understanding. Preserve code behavior, structured data, required syntax, and exact identifiers.

Preserve existing document filenames and paths. Never rename, move, or renumber existing documents to normalize titles, categories, prefixes, or numeric padding; external systems may link to their exact paths. Apply naming conventions to new files only and edit existing content and metadata in place.

Use the Humanizer skill whenever writing or revising user guides. Write for developers who have not read the project conversation: explain what each command changes, show defaults and configuration examples, and distinguish working features from planned ones. Keep commands and examples executable.
