Read testing.approach from config (default flexible).
Flexible permits tests before or after code within the selected placement.
For tdd, each implementation task must describe one red-green-refactor cycle: write a focused test first, run it and observe failure for the intended missing behavior, implement the minimum behavior to make it pass, then refactor while keeping relevant tests green.
Fix setup, import, or syntax errors rather than treating them as the intended red result.
Record the red and green commands and observed outcomes in the task completion notes; if the test already passes, report that instead of claiming a red phase.
Documentation-only tasks use suitable validation rather than a forced TDD cycle.
Final passing evidence alone does not prove TDD was followed.
With tdd selected for delivery, tasks.md must contain one fenced `yaml cliewen-tasks` block: version: 1 and tasks keyed by every checkbox's unique numeric ID (for example "1.1"). Each entry declares method (tdd, characterization, refactor, or verification), command as an executable/argument list, tests as explicit file paths, and implementation as explicit file paths. Non-tdd methods require a reason reviewed with the task plan; configuration and tooling changes that alter behavior still need tdd. Use the installed package's docs/configuration.md Test-driven development section for the complete format and executable examples.
Before changing a task's declared files, run cliewen-openspec tdd start --change <name> --task <id>. Run the declared command through cliewen-openspec tdd run --change <name> --task <id> --phase red --reason "<intended missing behavior>" -- <command and args>, then implement and record --phase green. A red run keeps its nonzero exit code; inspect its output before proceeding. Keep the tests unchanged between red and green. Record another green run after refactoring; a new test change needs another start/red/green cycle.
For characterization, start before adding the test, record a passing --phase baseline against unchanged production, then --phase green after any production work. For refactor, start with existing tests, record a passing baseline, then green with unchanged tests. For verification exceptions, start before work and record --phase verify using the agreed check. List every relevant file and review the declared verification boundary.
The recorder appends command output and file hashes under .cliewen-openspec/tdd/<change>.jsonl. Preserve this local history and failed attempts; do not invent or hand-edit events. Ensure tdd/ is ignored by .cliewen-openspec/.gitignore before recording; existing ignores are preserved by update. Missing history is unverified. A changed task definition needs a new start and honest verification, never a retroactive red claim.
After actual task verification, mark tasks complete and run cliewen-openspec check --change <name>. In tdd mode, completion checks remain active even when product evidence is disabled. Finish task notes and commit inputs before collecting final revision-bound evidence. History does not prove failure cause or human review and does not prevent production writes. Discovery and combined no-delivery closure do not require this delivery history.
Keep final revision-bound evidence collection and the completion check as untracked workflow follow-up, outside numbered checkboxes. A final verification task can record a real regression or documentation check. Do not use cliewen-openspec check as a recorded task command: it would assess its own unfinished history while the recorder is locked.
